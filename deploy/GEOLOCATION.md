# Точка ферми й контури полів

## Як користуватися

1. Відкрийте **Моє господарство** (`/farm`).
2. У блоці «Де розташована ферма» знайдіть село/місто, виберіть результат і уточніть місце натисканням на карту. Або введіть широту й довготу вручну.
3. Натисніть **Зберегти точку ферми**. Прогноз використовуватиме збережену точку. Назва й координати відображаються поруч із прогнозом.
4. Відкрийте **Мої поля** (`/fields`), введіть назву поля. Карта для нового поля відкриється біля збереженої ферми; якщо ферма ще не задана, буде огляд світу без вибраної точки.
5. На карті послідовно поставте маркери по периметру поля. Починаючи з третьої вершини карта показує контур. Вершини можна перетягувати, останню — скасувати, контур — очистити.
6. Натисніть **Завершити контур**, потім **Зберегти поле**. Повторно відкрити карту можна кнопкою **Карта / редагувати**.
7. Посилання **Погода для цього поля** відкриє прогноз для точки всередині контуру. Альтернативно виберіть поле у списку над прогнозом на сторінці господарства.

Точка прогнозу всередині контуру обчислюється з намальованої межі та не претендує на вимірювання погоди на всій площі. У розділі «Окрема точка прогнозу» можна задати власні координати, які матимуть пріоритет. Якщо прибрати окрему точку, використовуватиметься контур. Якщо немає ні точки, ні контуру, прогноз недоступний; координати ферми автоматично не підставляються замість поля.

Пошук населеного пункту на карті поля лише переміщує карту: він не створює межі й не записує координати населеного пункту як координати поля. Контур є допоміжним записом користувача, а не підтвердженою кадастровою межею. Задана вручну площа поля не змінюється за контуром.

## Збереження і сумісність

Після багатокористувацької міграції профіль зберігається як JSON-документ `farm_profile.json` у `chats.db/user_documents` з `user_id`. Фізичний старий `data/farm_profile.json` лишається архівним джерелом міграції. Запис в один спільний JSON-файл порушив би ізоляцію користувачів, тому вебінтерфейс оновлює особистий документ у SQLite.

Оновлення координат виконується транзакційно: читає старий документ, змінює лише `latitude`, `longitude`, `location_name`, записує його назад. `crops`, старий `location` та інші відомі й невідомі ключі залишаються. Нова назва локації має пріоритет перед старим `location`.

У полів додаються необов'язкові `latitude`, `longitude`, `location_name`, `boundary`. Межа — GeoJSON Polygon з порядком координат `[довгота, широта]`. Допускається один замкнений контур без отворів, 3–200 різних вершин. Самоперетини, незамкнені/вироджені контури та координати поза діапазоном відхиляються. Старі поля без цих ключів залишаються працездатними; старий клієнт, що не передає межу чи координати під час редагування, їх не видаляє.

Для геолокації окрема міграція схем не потрібна. Для старої однокористувацької інсталяції спочатку потрібна [міграція користувачів із резервною копією](MULTIUSER.md). Новий код не виконує production-міграцію автоматично.

Збережений кліматичний звіт не перераховується після зміни місця. Інтерфейс показує точку старого звіту та попередження. Прогноз погоди використовує актуальну збережену точку незалежно від старого звіту.

## API

Усі маршрути вимагають сесію користувача; зміни також вимагають чинний CSRF-заголовок `X-Agro-Request: 1` та допустимий Origin.

- `GET /api/farm/location` — збережена точка поточного користувача; невідомі координати повертаються як `null`.
- `PUT /api/farm/location` — `{"latitude":49.85,"longitude":29.46,"location_name":"Ферма"}`. Широта −90…90, довгота −180…180; значення мають бути скінченними. Обидва значення `null` очищають точку. Одне пропущене значення при заданому іншому відхиляється.
- `GET /api/locations/search?q=назва` — ручний пошук населеного пункту, до 8 результатів; сам пошук не змінює профіль.
- `POST /api/fields`, `PUT /api/fields/{id}` — наявні маршрути, що також приймають точку та/або `boundary`.
- `GET /api/weather` — прогноз для ферми.
- `GET /api/weather?field_id=ID` — прогноз лише для власного поля; чуже/невідоме поле повертає 404, поле без точки/межі — 503 із поясненням.

Кеш прогнозів і пауза після помилки розділені за користувачем, полем та координатами. Зміна координат одразу змінює ключ кешу. Для поточної назви локації не використовується стара назва з кешу. Збережені контури не додаються повністю до AI-промпту, щоб не витрачати контекст на сотні координат.

## Картографія та зовнішні сервіси

Leaflet 1.9.4 зберігається локально в `static/vendor/leaflet` разом із ліцензією. JS і CSS перевірені за SHA-256 з [офіційного посібника Leaflet](https://leafletjs.com/examples/quick-start/). Немає необхідності завантажувати JS із CDN при відкритті сторінки.

Картографічні тайли завантажуються браузером з OpenStreetMap з видимою атрибуцією та політикою referrer для тайлів, що передає лише origin при зверненні до стороннього сервера. Немає попереднього масового завантаження тайлів. Джерело: [правила використання тайлів OSM](https://operations.osmfoundation.org/policies/tiles/).

Назва населеного пункту передається на сервер Agro AI, а потім у [Open-Meteo Geocoding](https://open-meteo.com/en/docs/geocoding-api); пошук запускається кнопкою або Enter. У разі недоступності зовнішнього пошуку/тайлів ручне введення координат лишається доступним. Наявний `OPEN_METEO_API_KEY`, якщо заданий, використовується сервером і не передається браузеру.

Dockerfile уже копіює `static/`, тому нові JS/CSS і Leaflet потрапляють у звичайну збірку. Compose, Caddy, HTTPS та адреса зберігання production-даних не змінюються.

## Перевірки

```bash
.venv/bin/python -m pytest -q
```

Перевіряються запис/читання профілю, збереження `crops` та довільних ключів, діапазони, невідомі координати, приватність, CSRF, прогнози ферми й полів, зміна кешу, GeoJSON, відхилення самоперетинів, точка всередині увігнутого контуру, робота старих полів/клієнтів і помилки геопошуку.

Окремо виконана браузерна перевірка: пошук/збереження/перезавантаження ферми, малювання/перетягування/збереження/повторне відкриття контуру, вибір прогнозу поля та мобільна ширина 390 px. Для перевірки пошуку/прогнозу використовувалися контрольовані відповіді; карта завантажувала реальні тайли. Реальні production-дані не використовувалися.
