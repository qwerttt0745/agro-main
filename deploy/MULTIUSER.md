# Міграція Agro AI на кількох користувачів

Ці команди — інструкція адміністратору. Міграція production автоматично не запускається.
Наявний пароль, scrypt-параметри, ID записів і старі чинні сесії зберігаються.
Compose, Caddy, HTTPS, шляхи `/opt/agro-data` та `/app/data` не змінюються.

## Що змінюється

- `auth.db`: `users` (унікальний логін, scrypt-хеш, сіль, дата, активність, версія сесій), `sessions.user_id`.
- `chats.db`: власники чатів, повідомлень, фото, полів і фото етикеток.
- `user_documents` у `chats.db`: профіль і кліматичний звіт із `farm_profile.json` та `site/summary.json`, прив'язані до старого користувача.
- Старий `auth_credentials.json` і вихідні JSON залишаються без змін як архів. Після міграції застосунок читає акаунти та приватні профілі з SQLite. Редагування старих JSON більше не оновлює профіль у застосунку.
- Новий користувач отримує порожні приватні дані. Без його координат погода недоступна. Основну точку ферми можна задати на сторінці «Моє господарство». На сторінці «Мої поля» можна зберігати контури полів і переглядати прогноз для них. Деталі — у [GEOLOCATION.md](GEOLOCATION.md).
- Загальними залишаються публічна агрономічна бібліотека/RAG та завантажені офіційні реєстри. Не додавайте персональні документи до спільного RAG. Вміст серверного індексу в рамках локальних тестів не перевірявся.
- Перевірки власника діють для HTTP, фото, редагування/видалення етикеток, RAG і Live. `ContextVar` переносить перевірену особу в worker threads; за відсутності особи приватні операції відмовляють у доступі.
- Ліміт входу: 5 спроб / 15 хвилин для пари IP + логін. Окремий широкий ліміт 100 незавершених/невдалих спроб на IP захищає від перебору різних логінів. Успішний вхід очищає лише лічильник своєї пари. Старий спільний лічильник `attempts` більше не використовується для входу; новий допоміжний `login_attempts` створюється без зміни акаунтів. Cookie — HttpOnly/Secure/SameSite=strict, TTL 14 діб.

## Перед серверним оновленням

1. Збережіть поточну ревізію коду або старий Docker image для відкату.
2. Перевірте вільне місце: потрібна повна копія SQLite та JSON, плюс місце для rollback-журналів SQLite.
3. Перенесіть новий код і зберіть image. Не запускайте новий застосунок до міграції:

```bash
docker compose build app
docker compose stop app
```

Зупиніть також сторонні CLI/import-процеси, які пишуть у ці бази. `--offline` є явним підтвердженням адміністратора: команда не може перевірити всі сторонні процеси. Caddy може залишатися запущеним.

## Міграція

```bash
docker compose run --rm --no-deps app python -m scripts.migrate_users --offline
```

Команда спочатку читає старі credentials і перевіряє, що міграцію ще не виконано. Потім створює `/app/data/backups/users-<час>/` (на хості `/opt/agro-data/backups/...`):

- SQLite backup API для SQLite-файлів; `integrity_check` та `foreign_key_check`;
- копії JSON, включно з хешем пароля; права каталогу 700, файлів 600;
- SHA-256 маніфест і його перевірка перед зміною схем.

Каталоги `backups`, `chroma` та `hf-cache` не копіюються. Кеш моделей Hugging Face може містити символьні посилання — він виключається до обходу файлів. Посилання замість приватних SQLite/JSON чи каталогів із даними відхиляються з указанням відносного шляху. Книги, Chroma-індекс, API-ключі та `.env` не входять у цю міграційну копію: міграція їх не змінює. Зберігайте також звичайну повну серверну резервну копію.

Зміни обох приватних SQLite-баз виконуються в одній транзакції через ATTACH із rollback-журналами. Помилка до commit відкочує транзакцію. Після помилки не запускайте застосунок, доки не перевірите копію/стан; за потреби виконайте відкат нижче. Повторний запуск після успішної міграції відхиляється, акаунти не перезаписуються.

Збережіть шлях резервної копії, надрукований командою. Додаткова перевірка:

```bash
docker compose run --rm --no-deps app python -m scripts.migrate_users --verify /app/data/backups/users-REPLACE_WITH_TIMESTAMP
```

Лише після успішної перевірки:

```bash
docker compose up -d app
```

Увійдіть старим паролем, перевірте історію, фото, поля та господарство. Перевірте нового користувача в іншому браузері/приватному вікні.

## Користувачі

Пароль вводиться двічі через getpass, не передається аргументом і не друкується.

```bash
docker compose exec app python -m scripts.create_user --username oleksii_test
```

Існуючий логін відхиляється. Публічної реєстрації немає.

```bash
docker compose exec app python -m scripts.set_password --username oleksii_test
```

Зміна пароля стосується лише цього користувача, відкликає лише його сесії та не змінює старий JSON. Невідомий логін не створюється автоматично.

## Відкат

Відкат повертає стан на момент копії; нові записи після міграції не ввійдуть у стару базу. Команда спочатку зберігає додаткову перевірену копію поточного стану. Відновлення кількох файлів не є атомарним: у разі переривання повторіть відновлення з тієї самої копії, не запускаючи застосунок.

```bash
docker compose stop app
docker compose run --rm --no-deps app python -m scripts.migrate_users --offline --restore /app/data/backups/users-REPLACE_WITH_TIMESTAMP
```

Після відновлення поверніть стару ревізію коду / старий image, потім запустіть app. Новий код навмисно відмовляється запускатися зі старою схемою. Не запускайте стару версію на новій базі: вона не забезпечує ізоляції користувачів.

## Локальні перевірки

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Тести використовують тимчасові каталоги, справжній scrypt, реальну авторизацію та SQLite. Перевіряються міграція, старий cookie, два користувачі, HTTP/Live-ізоляція, паралельний AI-контекст, зміна пароля, пошкоджена копія, відкат, транзакційна помилка й перезапуск окремого процесу Uvicorn. Зовнішні AI-виклики замінені тестовими відповідями.

Для окремого локального стенда можна задати `AGRO_DATA_DIR=/абсолютний/шлях/до/тестових/даних`. За замовчуванням залишається попередній каталог `data/`. `AGRO_COOKIE_SECURE=false` дозволено лише для localhost/127.0.0.1, на сервері його не змінюйте.
